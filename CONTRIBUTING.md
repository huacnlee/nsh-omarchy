# Contributing Guide

Contributions are welcome. If you find a bug or have an idea, please open an issue or submit a pull request.

Please write clean code that follows the style and organization of the existing code, and make sure all tests pass.
Please submit **one PR that does one thing**: it is easier to review and faster to merge.

Before writing code, read [AGENTS.md](AGENTS.md) (the rules and commands) and [DESIGN.md](DESIGN.md) (the visual
language and the rules for code).

## Scope: what nsh-omarchy accepts

nsh-omarchy is the Omarchy presentation of NSH's components: square geometry, one accent, foreground-tinted state
fills, a visible focus border, compact desktop type and keyboard-first controls, with colors that follow the system's
Omarchy theme. It ports [gpui-omarchy](https://github.com/huacnlee/gpui-omarchy) to NSH, and both follow
[Omarchy Style](https://github.com/huacnlee/omarchy-style).

Welcome, with no prior issue:

- **Bug fixes**, in Rust or TSX, on any platform NSH supports.
- **Fidelity to Omarchy**: a state, spacing, motion or theme detail that does not match Omarchy Style or gpui-omarchy.
- **Completing existing components** with options common in their domain: what gpui-omarchy, GPUI Kit's components
  and other well-known libraries offer for that kind of control.
- **Accessibility and keyboard**: roles, names, focus order and visible focus.
- **Performance** of a component's rendering or updates.

A new component, or an option shaped by one app's workflow, needs an issue first (the feature request template) and
a maintainer's agreement. It is accepted when it is a common control of desktop apps, works the same in Rust and TSX,
and draws on an `nsh-base` behavior or an NSH primitive.

The boundary with NSH:

- **Behavior belongs to `nsh-base`.** Focus, keyboard, popups, dismissal and accessibility that every styled library
  would need go upstream to [NSH](https://github.com/longbridge/nsh), following its contributing guide. This crate
  does not fork or rebuild them.
- **The look belongs here.** Colors, sizes, borders and motion come from `tokens` and the theme; an app's own look
  stays in the app.
- **Do not change NSH to fit this crate.** Solve it here first, with NSH's existing APIs.

## API design

[docs/api.md](docs/api.md) is the public API, frozen from 0.1.0. A later 0.x release only adds: new components, new
optional props, new events, new enum variants and new shorthands. Names, constructor arguments, shorthands and events
that shipped do not change; a better name is added beside the old one, which stays.

- **Rust and TSX are one API.** A component is one `#[component]` in `src/ui/`; TSX uses the Rust names in camelCase
  (`on_open_change` is `onOpenChange`), and each event hands one object.
- **A constructor takes the required content; everything else is a setter** with a default. Common variants have
  shorthands (`.primary()`, `.small()`), generated in `src/ui/shorthand.rs`.
- **Names follow NSH first, then gpui-omarchy and GPUI Kit.** Where `nsh-base` has the component, use its name and
  event words (`on_press`, `on_change`, `on_select`).
- **Public types grow without breaking.** Public enums and options structs are `#[non_exhaustive]`, with `Default`
  and builder setters; data types have no public fields across the crate boundary.
- **Identity is a string**, `value` or `id`, never an index. Strings in props and events are `SharedString`.

## AI-Assisted Contributions

AI-assisted contributions are welcome, including pull requests whose code was entirely generated by AI. What matters
is that the change is necessary, focused and validated; the contributor is responsible for the result.

Before opening a pull request, make sure that:

- The problem is real, and a new feature is within the scope above.
- The API and implementation follow the existing patterns, [AGENTS.md](AGENTS.md) and [DESIGN.md](DESIGN.md).
- You reviewed the code and tested it: headless tests through the public API in `tests/`, the TSX gallery's tests for
  the TSX face, and a look on screen for anything visible.
- The diff is as small as practical: no unrelated refactors, cleanup or formatting. Reproduce a defect and fix its
  cause rather than hiding it behind retries or guards.

### Describe public API changes

A pull request that adds or changes anything public — a constructor, setter, shorthand, event, data type, enum
variant, token or theme function, or its TSX face — lists it under `## Public API`, with the signature as a reviewer
would read it in `docs/api.md` and one line on what it is for, and updates `docs/api.md`. A change to a shipped item
goes under `## Breaking Changes` with a `diff` block, and says why it cannot be an addition.

## Commits and pull requests

All changes go through a pull request against `main`; nothing is pushed to `main` directly. Pull requests are squash
merged, so the pull request's title becomes the commit on `main`.

Commit subjects and pull request titles name the area first, then say what changed as an imperative sentence:

```
<area>: <What the change does>
```

- The area is the part of nsh-omarchy the change is about, in lower case: a component by its name in snake case
  (`button`, `date_picker`, `data_table`, `context_menu`), a family when the change spans its components (`actions`,
  `choices`, `fields`, `navigation`, `overlays`, `data`, `display`, `charts`), or `theme`, `tokens`, `tsx` (the native
  module and the TSX face), `gallery`, `tsx_gallery`, `website`, `docs`, `ci`, `release`. Name one area only: for a
  change that spans several, name the part it is mostly about.
- The sentence starts with a capital letter, uses the imperative mood, has no trailing period and fits in about 72
  characters with its area. It says what the change does for an app, not which files moved.
- No conventional prefixes (`fix:`, `feat:`, `chore:`).
- The body (optional for small changes) explains why, wrapped at 72 columns.

Examples:

```
select: Add a clear button for a value that may be empty
theme: Follow a theme change made while a dialog is open
overlays: Keep the keyboard focus inside the newest dialog
website: Run the TSX gallery in the browser
release: Publish 0.1.1
```

### Reviewing

A review presents, in order: the pull request's purpose (the problem and the scope of the changes), whether the
requirement and approach are reasonable, then concrete findings, the validation performed and its limits. Scope comes
first: a pull request that adds public API is checked against "Scope" and "API design" before its implementation is
reviewed.

Every pull request that changes what is drawn includes screenshots in both themes (Tokyo Night and Flexoki Light).
Reviewers check that the tests and screenshots cover the states the pull request claims: hover, pressed, focus,
disabled, open and closed.

## Releases

A release is a pull request too:

1. A `release: X.Y.Z` pull request bumps `version` in `Cargo.toml` (and `Cargo.lock`) and the version in the README
   and `docs/api.md` where it appears.
2. After it merges, tag the merge commit on `main` as `vX.Y.Z`, run `cargo publish`, and create the GitHub release
   from the tag with the changes since the previous release.

## Development and Testing

You need Rust (stable), the `nsh` CLI and, for the website, [bun](https://bun.sh). See the README's "Developing".

```sh
cargo test                                         # every component headless
cargo clippy --all-targets                         # no new warnings in the code you touch
cd examples/gallery && nsh run                     # the Rust gallery, a page per component
cd examples/tsx-gallery && nsh check && nsh test   # the TSX gallery's tests, against this checkout
cd website && bun install && bun run gallery && bun run build && bun run test
```

Run the galleries for any visible change, in light and dark, and with the keyboard.
